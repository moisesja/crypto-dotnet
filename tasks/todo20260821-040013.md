# Fix flaky CI test: Secp256k1_IsAlwaysFixedWidthCompact first-byte assertion

Branch: `fix/transferable-key-validation-issue-30` (folded into PR #31 at the owner's request;
originally prepared on `claude/wonderful-meitner-npokuk`)

## Problem

PR #31's Windows `build-test` job failed on
`NetCrypto.Tests.KeyStore.AlgorithmEncodingTests.Secp256k1_IsAlwaysFixedWidthCompact`, a test
the PR does not touch. The test is flaky by construction: line 84 asserts
`signature[0].Should().NotBe(0x30, ...)` on a 64-byte compact (r‖s) secp256k1 signature made
with a freshly generated random key. The first byte of `r` is effectively uniform over runs, so
roughly 1 in 256 runs a perfectly valid compact signature legitimately begins with `0x30` and
the suite goes red — exactly what happened on PR #31's head `23f8bad` (the same test passed on
the previous head; ubuntu/macos passed on the same commit).

The assertion is also redundant: `HaveCount(64)` plus the successful compact `Verify`
round-trip already prove the output is fixed-width compact, not DER. The sibling DER tests
(lines 43, 132–133) assert `== 0x30` on actual DER output, which is deterministic and stays.

## Scope decisions

- Test-only change: remove the probabilistic assertion, keep (and not weaken) the deterministic
  contract — 64-byte width and compact verification round-trip.
- Leave a comment stating why there is no first-byte assertion, so it is not reintroduced.
- No production code, no public API, no version/changelog change (test-only, not released
  behavior).
- Land as part of PR #31 — the repository owner explicitly asked for this fix to be included
  there after the flake turned that PR's Windows leg red.

## Review

- **Fix**: `AlgorithmEncodingTests.Secp256k1_IsAlwaysFixedWidthCompact` no longer asserts on
  `signature[0]`. The deterministic contract is kept intact and slightly strengthened in prose:
  `HaveCount(64)` now states the fixed-width r‖s claim, and the compact `Verify` round-trip
  remains. A comment explains why no first-byte assertion belongs there, so it is not
  reintroduced.
- **Empirical proof**: a scratch harness (`scratchpad/flakeproof`, not committed) generated
  5,000 fresh secp256k1 keys with `DefaultKeyGenerator`, signed the same payload via
  `DefaultCryptoProvider`, and observed 18 signatures whose first byte was `0x30` (expected
  ~19.5 at 1/256); all 18 verified successfully. The removed assertion would have failed each
  of those runs — it rejected valid output by construction.
- **Verification**: with SDK 10.0.400 — `dotnet build NetCrypto.sln --configuration Release
  -warnaserror`: 0 warnings, 0 errors. `dotnet test --filter "Category!=NativeFFI"` (this
  environment has no native BBS library, matching CI's supported BBS-absent mode):
  1,188/1,188 main + 21/21 external-store tests passed, including all 9 `AlgorithmEncodingTests`.
- **Scope**: test-only; no production code, no API, no version metadata. The revert-proof rule
  for regression tests does not apply — no production behavior changed; the empirical harness
  serves as the proof that the removed assertion was wrong.
- **CI corroboration**: a single re-run of PR #31's failed Windows job on the identical commit
  (`23f8bad`, zero code changes) went green, independently confirming the flake diagnosis. The
  owner then asked for this fix to be part of PR #31, so it was cherry-picked onto
  `fix/transferable-key-validation-issue-30` and re-validated there.
