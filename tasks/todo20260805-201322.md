# Issue #23 — Accept RFC 8812-valid high-S ES256K signatures

## Goal

Address GitHub issue #23 by making the general-purpose secp256k1 verification path accept both valid ECDSA `S` representations while preserving low-S signing, malformed-input behavior, and the public API.

## Scope and decisions

- Change only `DefaultCryptoProvider`'s secp256k1 verification policy; recoverable signing/recovery semantics remain unchanged.
- Normalize a valid high-S compact signature to its mathematically equivalent low-S form before calling the NBitcoin/libsecp256k1-style verifier.
- Keep 64-byte compact `R || S` encoding, SHA-256 prehashing, and low-S output from signing unchanged.
- Return `false` for malformed length, zero/out-of-range scalars, wrong key/data, and corrupted signatures; do not turn verification failures into exceptions.
- Document the intentional policy on the public `ICryptoProvider.Verify` surface and in the PRD/README or changelog locations that describe secp256k1 behavior.
- Do not add an opt-in strict flag: issue #23 requires interoperable general ECDSA behavior by default, and adding policy surface is unnecessary for the stated use case.

### Negative control — the regression test is genuine

The decisive check the first session did not record: comment out the two-line `TryNormalize`
call, rebuild, and re-run only the new tests. Both fail, and they fail at exactly the high-S
assertion rather than incidentally:

```
Failed Verify_Secp256k1_HighSEquivalent_AcceptsRfc8812Signature   (line 316)
Failed Sign_Secp256k1_RemainsLowS

  through its high-S twin (iteration 0), but found False.
```

Restoring the two lines makes both pass, and `diff` against a pre-control backup confirms
`DefaultCryptoProvider.cs` is byte-identical to before the experiment. So the tests fail without

### Adversarial pass (re-run on resume)

An independent adversarial agent probed the boundary with a standalone console project outside the
repo. It found **no exploitable defect**, with running-code evidence rather than reasoning alone:

- **Forgery — SAFE.** Normalization is the map φ(r,s) = (r, min(s, n−s)); the accept set is exactly
  φ⁻¹(old accept set), so it doubles and every new member is the S-negation of a signature that
  already verified. Empirically: 50k chosen-high-S candidates against a chosen message and 500k
  random 64-byte signatures, 0 accepted, 0 exceptions. R-malleation `(n−r, s)` still rejected.
- **Null/exception safety — SAFE.** `TryNormalize`'s bool means *"was high-S"*, not *"succeeded"*,
  and it assigns a non-null `normalized` on **both** paths, so it can never yield true-with-null.
  Confirmed against the pinned upstream source and over 200k runtime inputs.
- **Scalar boundaries — SAFE.** 15 boundary pairs and 8 lengths differenced `main` vs branch:
  identical except the three intended high-S lines. `Negate(0) == 0`, so a zero scalar survives
  normalization unchanged and is still rejected inside `SigVerify`; `n−s` for `s ∈ [1, n−1]` stays
  in range, so normalization can never produce an overflowing scalar.
- **Non-secp256k1 — SAFE.** The `main`→branch differential changed exactly three lines, all
  secp256k1 high-S. Ed25519, P-256/384/521 and BLS lines byte-identical.

Three findings were acted on rather than waved off:

1. **The added comment was factually wrong.** It claimed zero scalars "are never normalized"
   because parsing rejects them. Parsing does *not* reject zero — `Secp256k1Recoverable.cs:101-102`
   says so verbatim ("NBitcoin's compact parser only rejects overflow (>= n)") and adds an explicit
   zero check the verify path lacks. The outcome was right for the wrong stated reason. Comment
   rewritten to give the actual argument (`Negate(0) == 0`; range closure under negation).
2. **P-256/384/521 have always accepted the `(R, n−S)` twin** — neither FIPS 186-5 nor .NET's
   `ECDsa` imposes low-S. So this change made secp256k1 *consistent* rather than novel, and the
   original docs singling out secp256k1 as "the curve whose bytes aren't a unique ID" were
   misleadingly narrow — the exact discoverability failure issue #23 complains about. Pinned with a
   new `Verify_NistEcdsa_AlreadyAcceptsNegatedS` theory over all three curves, and the warning was
   rewritten against ECDSA in general in `ICryptoProvider`, README, `RecoverableSignature`, sample.
3. **Test naming and a coverage gap.** `InvalidCompactScalars` also listed *valid* scalars
   (`n−1`, `n/2`, `n/2+1`) that fail only because they aren't signatures for that key — renamed to
   `NonVerifyingCompactScalars` with the two rejection reasons spelled out. Added the missing
   assertion that `(n−R, S)` and `(n−R, n−S)` stay rejected, which is the property that proves the
   accept set widened by exactly one encoding.

### Downstream blast radius (closes the pass's one UNVERIFIED item)

A sweep of all eight NetCrypto consumers (net-did, zcap-dotnet, didcomm-dotnet, dataproofs-dotnet,
credentials-dotnet, net-wallet-sdk, opaqai-wallet-platform, net-wallet-mcp):

- **No consumer keys replay/dedup on signature bytes.** Every candidate resolved to a non-signature
  key — zcap-dotnet's nonce store keys on the document `id`, net-did's webvh `proofIds` on the proof
  `id`, its entry hash deliberately excludes the proof, and the wallet audit CIDs cover no signature
  bytes. This is the negative result that makes the change safe downstream.
- **No downstream test asserts `ICryptoProvider.Verify` rejects high-S.** The two high-S rejection
  tests (`EncodeSigned_HighS_IsRejected`, `HighSSignature_IsRejected`) target net-did's own
  `EthereumTransaction` EIP-2 guard, which is untouched, so they keep passing.
- All secp256k1 verification funnels through two dataproofs-dotnet files (`JoseCryptoProvider`,
  `CoseCryptography`) — the ES256K path issue #23 was filed from. zcap-dotnet is latent only
  (`ZcapSuiteCatalog` is a closed Ed25519/P-256 set). personal-data-store has no NetCrypto reference.
